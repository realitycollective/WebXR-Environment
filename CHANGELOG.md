# Changelog

Change log for the Reality Collective WebXR Environment Extensions packages. All four packages are versioned and released together; the version below is the one carried by the `v<version>` release tag.

The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and the project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html). Preview builds are not listed separately. The entry for a version accumulates while its previews are published, and is dated when that version is released.

## [0.1.1]

### Fixed

- `@realitycollective/threejs-environment` - a gradient sky never changed after its first frame. Choosing `night` in the playground moved the lights and the fog while the sky stayed at noon; only a solid sky, which is a plain `Color`, followed a transition. `applySky` refilled the pixels of the one `DataTexture` and set `needsUpdate`, but three.js converts an equirectangular `scene.background` into a cube map once per texture object and keeps that cube map until the texture is disposed, so the 2D texture was re-uploaded and the sky on screen never re-derived. The port now builds a fresh texture on every gradient change, swaps it in and disposes the previous one, which is what drops the cached cube map; the texture is 2 by 64 texels, so the extra upload during a transition is negligible and the cube conversion costs the same either way. The test that pinned the old in-place refill now pins the swap and the disposal instead. `@realitycollective/xrblocks-environment` inherits the fix. Found while photographing the live playground for the Reality Collective site, on a real GPU as well as in software rendering.
- `@realitycollective/threejs-environment` - `XrInputSourceLike` is exported. It was the element type of `XrSessionLike.inputSources` but not exported itself, so a consumer typing a fake session for a test had nothing to name, and TypeDoc flagged it as referenced but undocumented.
- CI - the staging deploy published under `--branch=pr-<number>` while the `-test` Pages project's production branch is `staging`, so only `pr-<n>.webxr-environment-test.pages.dev` aliases were ever created and the project's root URL was a 404. It now deploys as `staging` on every pull request and on every push to `development`, so `webxr-environment-test.pages.dev` serves the newest preview build, the same arrangement WebXR-UIExtensions already had.

## [0.1.0] - 2026-09-17

### Added

- `verify:pack` now lints the shape of what ships: publint over every package directory, with warnings counted as errors, and attw (Are The Types Wrong) over every packed tarball, resolving the published types under node10, node16 and bundler resolution. `cjs-resolves-to-esm` is ignored by design, because every package is ESM-only and a require() caller is expected to use a dynamic import. Both run offline on the tarballs the script already builds; `publint` and `@arethetypeswrong/cli` are dev dependencies. The script stays identical across the Reality Collective repositories.
- `verify:pack` now also type-checks the published declarations themselves, with library checking on, through `scripts/declaration-check.mjs`, runnable on its own as `node scripts/declaration-check.mjs`. Each package's declaration entry is compiled as a strict consumer would compile it, with `skipLibCheck: false`, under nodenext and then bundler resolution; a diagnostic inside the package fails the run, and diagnostics inside upstream declaration files are counted and ignored, because they are not ours to fix and would drown the signal. attw proves the published types resolve; this proves they compile, which is what a consumer with library checking on, or a package emitting declarations on top of ours, needs. The check is opt-in per repository, through `declarationCheck` in `scripts/release.config.json`, because only a foreign declaration can put a name into our emitted types that the build did not already check. This repository reaches around 950 of them, from the IWSDK and three.js typings the adapter is built against, and every run prints that count so the opt-in stays measured rather than habitual. It is the check that would have caught the bare `World` under Fixed.
- `@realitycollective/webxr-environment` - the engine-free core. `EnvironmentDirector` holds a sky (gradient or solid), fog (linear or exponential), an ambient light and a key light as plain data; interpolates between named presets over a host-supplied `update(deltaMs)`; pushes only the slots that actually changed to an `EnvironmentPort`; and applies passthrough as a suppression over what the app asked for, so nothing has to remember what to restore. A partial `EnvironmentSpec` inherits the slots it omits and turns off the ones it sets to `null`, which is what makes presets composable. Six example presets (`void`, `dawn`, `noon`, `dusk`, `night`, `overcast`) to copy, and `clearedFog`, the helper that makes fog easeable in.
- `@realitycollective/webxr-environment` - `AudioDirector`: a cue registry, a bus and master mix with mute kept separate from gain, per-cue retrigger policy (`overlap` / `restart` / `ignore`), a per-cue minimum retrigger interval, and voice tracking. The `AudioPort` is handed an absolute resolved gain and has no mixing left to do. A silent one-shot is never started; a silent loop is, so that unmuting mid-flight finds the ambience bed already running.
- `@realitycollective/threejs-environment` - the three.js adapter. Gradient skies become an equirectangular `DataTexture` generated by a pure function and regenerated in place across a transition; `Fog` / `FogExp2` are mutated rather than rebuilt while the kind holds; the key light is positioned from the direction light travels. Audio runs over `Audio` / `PositionalAudio`, and a play that arrives before its buffer has decoded is held rather than dropped, so the first press of a session is not silent.
- `@realitycollective/iwsdk-environment` - the Meta IWSDK adapter, driving IWSDK's own `DomeGradient`, light components, transform entities and `AudioSource` machinery rather than reaching past them to three.js. One-call `registerEnvironment(world)` setup that also registers the ECS system ticking both directors, converting IWSDK's seconds to the directors' milliseconds once. Fog is the one exception and is set on `world.scene`, since IWSDK has no fog component. Playback end is inferred by polling, because IWSDK reports only whether a source is playing; a voice that never starts is reaped with a warning rather than tracked forever.
- `@realitycollective/webxr-environment` - an **image-based lighting slot**. `IblSpec` is a gradient, an authored image or the host's own room probe, with intensity and a Y rotation, interpolated like every other slot. Without it a physically-based material had nothing to reflect: every host keeps the sky and the environment map as two separate facilities.
- `@realitycollective/webxr-environment` - **authored skies** (`SkySpec` kind `"texture"`, with intensity, rotation and blur) and an optional **horizon stop** on a gradient sky. The horizon colour exists because IWSDK's dome has always been a three-stop ramp and the adapter was deriving the middle colour; an app that puts a bright band at eye level can now say so and have both engines agree.
- `@realitycollective/webxr-environment` - **the sensing seam**. `EnvironmentPort.observe(host)` is the one inbound path: a port reports `unsupported` / `unavailable` / `pending` / `active` per feature with a sentence saying why, and reports measured lighting. `EnvironmentDirector.getSensing()` and `onSensing()` read it. A report never changes what the app asked for; it changes what the app can be told - which matters because a sensor that is doing nothing looks exactly like a sensor that is working.
- `@realitycollective/webxr-environment` - **depth occlusion**. `setOcclusion(spec)` reaches the port only while passthrough is on, and is remembered across passthrough changes. `OcclusionSpec` carries the union of what the hosts actually expose: three shader modes, a scope, softness, the WebXR session preferences (usage, data format, depth type, `matchDepthView`) and an update-rate cap. While occlusion is ACTIVE the sky is suppressed as well, because three.js stops drawing `scene.background` itself when its depth sensing runs.
- `@realitycollective/webxr-environment` - **light estimation**. `setLightEstimation(true | spec)` lets the host's measurement of the real room take over the ambient, key and ibl slots while it is measuring, and hands them straight back when it stops. The estimate arrives as the same spec types the app writes by hand, so it can be read, blended or ignored.
- `@realitycollective/webxr-environment` - **blend-mode-aware passthrough**. `setPassthrough` now takes `"opaque" | "alpha-blend" | "additive"` as well as a boolean, and `passthroughSuppresses` can differ per mode. On an additive display the rendered image is ADDED to the world, so a dark fog is invisible rather than dimming; an app can now do the opposite thing on each rather than choosing one compromise.
- `@realitycollective/webxr-environment` - **per-cue spatial attenuation** (`AudioCue.spatial`: reference distance, rolloff, maximum distance, curve) and a `ui` bus in the default set. All three hosts expose those four per source; the contract previously flattened them to one number chosen by the adapter.
- `@realitycollective/webxr-environment` - `EnvironmentPort.update(deltaMs)`, optional, called from the director's own `update`. Only sensor-backed ports need it: three.js reports depth through a renderer flag that flips some frames after the session starts, and a light estimate has to be read out of the current `XRFrame` or not at all.
- `@realitycollective/xrblocks-environment` - **a Google XR Blocks adapter**, EXPERIMENTAL, built on the three.js adapter the way `xrblocks-interactions` is built on `threejs-interactions`. Occlusion registers as a client of XR Blocks' `Depth` manager and picks its blur; light estimation reads the `Lighting` manager, which already owns the WebXR half. XR Blocks is never imported - its managers are described structurally, as in the other XR Blocks adapters in this estate - and anything configured before this adapter could ask is named in the report rather than dropped, including the warning that XR Blocks may be lighting the scene itself.
- `@realitycollective/webxr-environment` - **world sensing**, as a separate component on the same seam. `WorldSensingDirector` asks for planes, meshes and anchors, keeps one copy of each registry, and emits `added` / `updated` / `removed` by id so an app can spawn content on a new surface and drop it when the surface goes. Standing hit-test requests, anchor creation, and the host's own semantic labels passed through rather than mapped to a closed set. It reports detected geometry and creates none: a mesh's vertices are the runtime's buffers by reference, and what to draw on a table is the app's.
- `@realitycollective/threejs-environment`, `@realitycollective/iwsdk-environment`, `@realitycollective/xrblocks-environment` - world-sensing ports for all three hosts. three.js reads the `XRFrame` directly and measures a mesh once per `lastChangedTime`; IWSDK queries the entities its `SceneUnderstandingSystem` already made and casts through `EnvironmentRaycastTarget`; XR Blocks reads its `PlaneDetector` and `MeshDetector`, and reports anchors and hit testing as unsupported because it places objects for you rather than answering where a ray lands.
- `@realitycollective/webxr-environment` - `IblSpec` gained `{ kind: "estimated" }`: the reflections the host measured from the real room. It is a MARKER rather than data, because a reflection cube map is a live texture on a GPU and cannot be a `src` string without ceasing to be what it is. The adapter that measured it applies it; the others report that they cannot. Arrives on its own through `setLightEstimation({ ibl: true })`.
- `@realitycollective/webxr-environment` - **directional sound**. `AudioSpatial.cone` says how narrowly a cue points (inner and outer widths in RADIANS, like every other angle here, plus the gain outside), and `PlayOptions.facing` says which way this particular one is turned - the direction the sound travels, the same convention `KeyLightSpec.direction` uses. Both hosts want degrees and both point a source along +Z, because both are wrapping the same Web Audio panner, and each adapter converts. Without it a television, a PA horn and a person talking all played as glowing orbs of sound on every engine.
- `@realitycollective/webxr-environment` - `WorldSensingDirector.meshesLabelled`, the counterpart of `planesLabelled`. A wall arrives as a detected mesh as often as a plane, and having the helper on one side only also hid that the matching is case-insensitive.
- `demos/playground` - a standalone three.js/WebXR playground: preset transitions, a passthrough toggle that shows suppression restoring the environment exactly, and live bus/master sliders moving voices that are already sounding. It builds its own floor and objects, and binds a DOM event to `audio.play`, because both are the app's job.

### Fixed

- `@realitycollective/iwsdk-environment` emitted the same bare `World` in `EnvironmentSystem`'s base type that broke a consumer of the UI Extensions adapter on 9 September 2026. The cause is upstream: `@iwsdk/core` 0.5.3's `dist/ecs/system.d.ts` imports `World` from `'./world'` with no extension, the only such import in the package, and under the NodeNext resolution this repository builds with that import does not resolve (TS2835), so `World` was an unresolved name inside the host's own declaration and TypeScript's declaration emitter preserved it verbatim. `skipLibCheck` hid the error on both sides. It compiled for consumers only because `index.d.ts` happened to import `World` for another signature. The adapter now takes `createSystem` from its own `src/create-system.ts`, a wrapper whose return type names `World` through `@iwsdk/core`'s barrel, so the emitted base type no longer depends on that accident. The wrapper goes the day IWSDK ships `./world.js` there.
- `@realitycollective/iwsdk-environment` imported three.js's `Vector3`, `Quaternion`, `Fog` and `FogExp2` through `@iwsdk/core`, which only provides them by `export * from 'three'`. That resolves in node and in every demo, and fails a consumer whose Vite config excludes `three` from dependency optimization, which any app that transforms three's source does: esbuild cannot enumerate a star re-export it is not bundling, and the dev server stops with `No matching export in "@iwsdk/core" for import "Vector3"`, a message that names neither the package nor the cause. The audio, environment and world-sensing ports now import those classes from `three`, declared as a peer dependency (`>=0.170.0`, the range the three.js adapter carries), which every IWSDK application already has. `@types/three` is pinned to `0.185.4` across the workspace (root `overrides`), the typings for the super-three 0.185 the workspace runs, so the tree holds one copy of the three typings rather than the two that made the adapter's tests import `Scene` through `@iwsdk/core`. The Anatomy Atlas XR client reported the failure against the UI Extensions adapter; the estate sweep found the same import here.
- Two gates, shared with every Reality Collective repository. `packages/webxr-environment/test/import-surface.test.ts` runs `scripts/import-surface.mjs` over every published package and fails an import of a name that a dependency only re-exports from another package, and any bare import of a package the manifest does not declare. `packages/iwsdk-environment/test/prebundle.test.ts` runs the dependency optimizer of every bundler `scripts/release.config.json` names (`scripts/prebundle-check.mjs`) over the adapter next to `@iwsdk/core`, once with defaults and once with every package `@iwsdk/core` re-exports wholesale excluded, so the consumer path is exercised on every `npm test`. It runs on **Vite 7 and Vite 8**, because this fault belongs to a bundler rather than to bundling: Vite 7 optimizes with esbuild, which requires every named import to be statically enumerable and so rejects a name behind an external `export *`, while Vite 8 optimizes with rolldown, which resolves the same import lazily through a namespace object and accepts it. Testing only one of them would say nothing about consumers on the other. The versions under test are ordinary devDependencies installed under npm aliases, `vite-7` and `vite-8`, the same mechanism the workspace already uses for `three`; add an entry to `prebundle.bundlers` to support another. Each run also feeds the optimizer a **deliberately broken copy** of the adapter, carrying one extra module that imports a name the host only re-exports wholesale, and asserts the bundler's verdict matches that bundler's `detectsStarHops` flag. The probed name is discovered from the host's own surface rather than hard-coded, so it stays valid as that surface changes. This is what stops the check becoming decoration: on a permissive bundler a gate that can only pass reports safety it never verified, and the suite now fails if a bundler's strictness moves in either direction, or if no supported bundler can detect the fault at all. Transpiling uses the TypeScript compiler the repository already builds with, so no bundler is a hidden requirement of the harness itself. Both were red before this fix.
- **A hand ray is now cast from the hand.** The three.js world-sensing port used to bind every hit test to the viewer's reference space and mention in a detail string that hands were not really supported, which meant the most common AR gesture - point at the floor, place something - silently aimed from the head. It now looks the input source up by handedness, binds to its `targetRaySpace`, waits visibly while there is no such source, and unbinds when the hand goes away.
- **`HitTestRequest.offsetRay` is no longer dropped.** It becomes an `XRRay` (injectable, defaulting to the browser's) and is passed to the runtime. When no `XRRay` is available the request still works and the report says the offset was ignored, rather than quietly aiming somewhere else.
- **`WorldHit.distance` is filled where a host can fill it.** The three.js port poses the ray's own space once per frame and measures from there. IWSDK keeps its ray to itself, so it reports `null`, and the contract now says exactly what `null` means and what it does not.
- **Creating an anchor turns anchor detection on.** `createAnchor` used to hand back an id that nothing would ever update unless the app had separately asked to detect anchors - content pinned to it would never move again. The director now enables it and reports that it did.

### Notes

- The core has **no runtime dependencies at all**, and its architecture test asserts it: no engine, no service framework, no input contracts. No sibling package is imported, named in a type, or asserted against in a test either. Passthrough arrives through `setPassthrough(boolean)` rather than by reading a session, and a sound is played because the APP subscribed something to `play(cueId)` - if a source is present the app binds it, and if it is not, nothing here notices. Those two boundaries are what keep this package a leaf.
- The three.js adapter uses three.js's **own** depth-sensing occlusion, which has been in the renderer since r158 and draws its occlusion mesh before everything else. There is no hand-rolled depth-priming pass here: writing one would duplicate the renderer in the one place this estate cannot afford drift, GL state that three.js caches. What the adapter does instead is decide whether the request can be served - a session, the `depth-sensing` feature, gpu-optimized depth, a scope three.js can honour - and report the reason when it cannot.
- The IWSDK adapter takes an `occludables` option for `scope: "all"`, because IWSDK opts entities into occlusion one at a time and the entities are content, which is the app's. It never removes a `DepthOccludable` the app added itself. IWSDK 0.5.3 has no light estimation at all, and that is reported rather than left silent; both gaps are filed in [`docs/UPSTREAM_ENHANCEMENTS.md`](docs/UPSTREAM_ENHANCEMENTS.md) as items 6.1 and 6.2.
- World sensing is a **second director**, not more slots. Sky, fog and lighting are things the app describes and the host draws; planes and meshes are things the host measures and the app reads, and their consumers are placement, locomotion, physics and interaction rather than the eye. An app that wants only a sky pays for none of it.
- **A body solver was considered and declined.** No host exposes a body, so it fails the boundary test this repository is built on; see [`docs/BOUNDARY.md`](docs/BOUNDARY.md). Planes, meshes, anchors and hit test are real platform sensing but feed placement and interaction rather than the environment, and are recorded there as a separate component rather than as slots of `EnvironmentSpec`.
- Every slot the environment describes is a PLATFORM facility each host exposes differently - `scene.background` and `Fog` on three.js, `DomeGradient` and `AmbientLightComponent` on IWSDK. CONTENT is the app's: no geometry is created by either adapter, and the stock presets are examples to copy rather than art direction. See [`docs/BOUNDARY.md`](docs/BOUNDARY.md) for the boundary in full, and [`docs/UPSTREAM_ENHANCEMENTS.md`](docs/UPSTREAM_ENHANCEMENTS.md) for the gaps that belong to the other packages rather than this one.
